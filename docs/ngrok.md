# Ngrok Integration & Dynamic URL Discovery
**Project:** CustomKahoot
**Date:** April 2026

## Overview
This document summarizes the transition from utilizing static Local IP addresses to employing **Ngrok** for dynamic URL routing. This architectural change resolves the strict "same-network" requirement, allowing guests to join a hosted session from completely disparate networks (e.g., cellular data, different Wi-Fi routers) by creating a secure tunnel to the localhost environment.

## Conceptual Comparison: Local IP vs. Ngrok

| Feature | Local IP Routing | Ngrok Tunneling |
| :--- | :--- | :--- |
| **Network Constraint** | Devices must exist on the exact same Local Area Network (LAN). | Agnostic. Devices can connect from any global network interface. |
| **Client Isolation** | Fails entirely on public networks (universities, cafes) with AP Isolation. | Bypasses local AP isolation by routing through external servers. |
| **Security Layer** | Unencrypted (`http://`) traffic over LAN. | Secure SSL encryption (`https://` / `wss://`) out of the box. |
| **Latency** | Near-zero milliseconds. | Subject to external ISP routing and Ngrok server location. |

## Drawbacks & Considerations
While optimal for development and disparate testing, the free tier of Ngrok introduces specific constraints:

1. **Ephemeral URLs:** The public URL changes dynamically upon every daemon restart, breaking previously issued QR codes and session links.
2. **Rate Limiting:** Free tiers enforce strict connection velocity limits, triggering HTTP 429 (Too Many Requests) errors during burst connections (e.g., 30 students scanning a code simultaneously).
3. **Phishing Interstitials:** First-time connections are often presented with an interstitial "Visit Site" warning screen generated by Ngrok to prevent abuse, which introduces friction to the UX.
4. **Latency:** Routing real-time WebSocket traffic over the wider internet introduces millisecond delays compared to pure LAN routing.
5. **Security Exposure:** The localhost environment is exposed to the public internet.

## Technical Implementation (Method 2: Automated Discovery)

To prevent the administrative overhead of manually configuring the ephemeral Ngrok URL inside `application.properties` upon every launch, an automated discovery mechanism was implemented.

### 1. The `UrlDiscoveryService`
A dedicated Spring `@Service` was engineered to interrogate Ngrok's local management API.
*   **Mechanism:** Upon event launch (`/go-live`), the backend executes an internal `GET` request to `http://127.0.0.1:4040/api/tunnels`.
*   **Parsing:** A `RestTemplate` reads the JSON payload, parsing the `JsonNode` tree to extract the currently active `https` tunnel string.
*   **Resilience (Fallback):** If the Ngrok daemon is not running (e.g., throwing a `ResourceAccessException`), the `catch` block gracefully degrades the system to the legacy behavior: resolving `InetAddress.getLocalHost().getHostAddress()`.

### 2. Controller Injection
The `HostApiController.java` was refactored to utilize the `UrlDiscoveryService`.
*   The hardcoded Local IP generation block inside the `goLive()` method was stripped.
*   It now fetches the dynamically resolved Base URL and pushes it downstream to the frontend for accurate QR code generation.

### 3. Cross-Origin Resource Sharing (CORS) & WebSockets
Transitioning from `localhost` to `*.ngrok-free.app` constitutes a cross-origin context shift.
*   To ensure the bidirectional WebSocket streams powering the real-time game states (answering, locking, leaderboards) are not rejected by browser security policies, the Stomp configuration was relaxed.
*   In `WebSocketConfig.java`, the endpoint registration was appended with `.setAllowedOriginPatterns("*")` to permit the WebSockets to bind seamlessly regardless of the tunneling domain.

### 4. Bypassing the Ngrok Browser Warning (Programmatic Requests)
When using the free tier, Ngrok intercepts the first request from a new client with a "Visit Site" HTML warning page. While a user scanning a QR code can manually click through this via their mobile browser, automated/programmatic API requests (like JavaScript `fetch()` calls) cannot click buttons. If an API request hits this interstitial, it will fail because it expects JSON data but receives HTML.

To resolve this, a global `fetch` interceptor was injected into the core frontend JavaScript files (`host-setup.js` and `host-live.js`).
*   **The Mechanism:** The native `window.fetch` function is overridden to automatically append the HTTP header `ngrok-skip-browser-warning: "true"` to every outgoing request.
*   **The Result:** Ngrok's edge servers recognize this header and allow the programmatic HTTP requests to pass through the tunnel directly to the Spring Boot REST API without serving the interstitial warning page.
